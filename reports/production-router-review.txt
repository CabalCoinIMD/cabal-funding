The deployed router uses an extended swap struct containing minHopPriceX36.
The Explorer passes zero for this field. Its exact-input command is 0x10 with
actions 0x060c0f: swap, settle all input, take all output. The reviewed harness
mirrors this encoding, a 1% minimum-output tolerance and ten-minute deadline.
Both the router and quoter report the expected Robinhood PoolManager.

Passed in BOTH currency orderings
- Actual LaunchFactory CREATE2 token/hook deployment and single-sided pool seed.
- Buy/sell, exact-input/output: eight quoted trades equal actual execution.
- Correct 4% custom fee, 70/30 allocation, fixed treasury payout and independent
  platform-fee accounting. Quoting leaves no persistent hook charge.
- Missing ERC-20 approval, missing Permit2 allowance, expired deadline,
  insufficient minimum output and excessive required input all revert atomically.
- A stale quote fails after a price move; a fresh quote then succeeds.

- Unfillable exact-output trades are rejected by both router and quoter.
- Local payment through actual Intake code clears its exact allowance. This is
  contract execution only; no real oracle was admitted or asked to decide.

Liquidity limitation
The production quoter refuses an oversized sell that would only partially fill,
with NotEnoughLiquidity(bytes32), wrapped in UnexpectedRevertBytes. The observed
Explorer disables submission when a quote fails. A smaller fillable sell quotes.
This is liquidity behavior, not a promise that any sell size can execute.

Separately bypassing the UI on the LOCAL fork proved the raw router can partially
fill that exact-input CABAL sell, leave unspent CABAL with its trader, and tax only
the IMD actually received. That direct test is not the Explorer's user flow. Where
IMD is the specified amount, our hook intentionally rejects partial fills so a
prepaid charge cannot be retained on unfilled input.

Test harness corrections
The first attempt expected the quoter to accept a partial fill; verified quoter
source established the rejection above. The second attempt reused a depleted
simulated balance for the other ordering. Cases now restore the funded baseline.
Neither harness correction altered production hook or payment-worker code. The
latest run also includes LaunchToken's fixed 50,000 CABAL read-only eligibility
constant/view, verified after actual factory deployment in both orderings.

Limits and next steps
The current UI offers exact input only; exact-output coverage tests the deployed
router's additional functionality. No browser wallet interaction was performed.
Pin and publish the reviewed source only when authorized, then use its real public
repository and commit in the launch request. IMD's imported-code adaptation,
manifest, review panel and final deployed artifacts still need review. If IMD
changes executable code, rerun the suite on that revision. Recheck current router
addresses and quotes against the final pool before trading opens.

The funding worker is not a service hosted by IMD, and the game is not connected
to it. Configure its signer, limits, persistent storage, monitoring and verified
oracle result consumer separately before enabling payments.
